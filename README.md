# Campus Care

A student mental wellness platform built with Spring Boot and MongoDB, featuring an AI-powered resource recommender that combines vector search with LLM reasoning over multiple sources of student context.

Built as the final project for a NoSQL Databases course. I owned the entire backend — including the AI recommendation pipeline — solo, while two teammates handled the frontend refactor, documentation, and database design.

> "This should be in production." — Course instructor, after the final demo.

---

## What it does

Students complete a daily self-evaluation (stress, anxiety, sleep, mood, relationships, motivation) and can keep a free-text emotional diary. Based on that input, the platform recommends wellness resources — articles, breathing exercises, support lines — **with a human-readable explanation of why each one was chosen**, generated by an LLM that reasons over the student's actual words, not just their scores.

Gamification (points, streaks) and an admin panel (resource/category/phrase management, trend dashboards) round out the platform.

---

## The AI recommendation pipeline

This is the core technical piece of the project: a **Retrieval-Augmented Generation (RAG)** pattern, split into two distinct AI roles that each do what they're best at.

```
Self-evaluation + Diary entry
          │
          ▼
   Voyage AI (embeddings)
          │
          ▼
MongoDB Atlas Vector Search  ──►  Top 5 candidate resources
          │
          ▼
   Claude API (reasoning)
          │
          ▼
2–3 ranked resources + personalized explanation
```

**Voyage AI** converts the student's self-evaluation and diary entry into a vector embedding, which MongoDB Atlas Vector Search uses to retrieve the resources whose *meaning* is closest to the student's current state — semantic search, not keyword matching.

**Claude** then receives those candidates alongside the full context — the self-evaluation scores, the diary entry, and a static catalog of practical exercises — and does the actual reasoning: it selects the most relevant resources, avoids duplicates, and writes a natural-language explanation for each one. The explanation frequently references specific things the student wrote in their diary, not just their numeric scores — turning a generic recommendation into a genuinely personalized one.

Splitting retrieval (fast, cheap, embeddings-based) from reasoning (slower, context-aware, LLM-based) is what makes this pattern scale: full LLM reasoning over every resource on every request doesn't scale as the resource catalog grows, but reasoning over a short pre-filtered shortlist does.

## Tech stack

**Backend**
- Java 21, Spring Boot 3.3.5
- Spring Security with JWT authentication and role-based access control
- MongoDB (Spring Data MongoDB)
- MongoDB Atlas Vector Search
- Voyage AI (embeddings)
- Claude API (Anthropic) — reasoning and natural-language explanation generation

**Frontend**
- Vanilla JavaScript, Bootstrap
- Chart.js for progress visualization

## Engineering highlights

A few problems worth calling out, beyond just "connect API A to API B":

- **Multi-source prompt construction.** The recommendation prompt merges three independent context sources — structured self-evaluation scores, free-text diary entries, and a static exercise catalog — into a single coherent prompt, with graceful degradation when any one source is empty (e.g., a student with no diary entries yet still gets recommendations, just without diary-based reasoning).
- **Framework migration under pressure.** Started on Spring Boot 3.x, hit instability with embedded MongoDB subdocuments during development, and resolved it by downgrading to Spring Boot 3.3.5 / Java 21 and restructuring `logros_obtenidos` (achievements) into its own top-level collection instead of an embedded subdocument.
- **Security fix on the diary module.** The initial diary implementation filtered "my entries" client-side, which meant the API itself exposed every user's diary entries to any authenticated caller. Replaced it with server-side filtering scoped to the authenticated user's ID, closing a real data-exposure gap before it shipped.
- **Debugging across system boundaries.** Diagnosed and fixed a chain of integration issues that had nothing to do with business logic and everything to do with systems not talking to each other cleanly: a mismatched MongoDB write concern, a missing Atlas Vector Search index, credentials from two different providers being swapped, a duplicated route prefix causing a misleading 403, and a stale compiled class file masking a data problem as a code problem.
